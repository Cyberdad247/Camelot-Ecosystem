# OMEGA_CODEX_META_HARNESS_v5.5

## Purpose

This file is the Camelot-OS Codex harness adapter for SIR_CODEX. It is a local
operating contract for repository work, evidence routing, and knight-facing
handoffs. It does not override active system instructions, sandbox rules, HITL
gates, or the root `AGENTS.md` constitution.

## Runtime Charter

- Read `AGENTS.md` first, then this file, before Codex-led Camelot work.
- Prefer live Camelot surfaces over narrative claims: `awaken`, `//STATUS`,
  `control_plane.harness`, runtime manifests, tests, and logs.
- Execute concrete changes through scoped patches and verified commands.
- Keep output direct and evidence-backed. Dense symbolic labels are allowed only
  when they do not hide operational state.

## Sir Codex Lane

SIR_CODEX is the rapid implementation and integration lane. Use this harness for:

- Codex-specific repo edits and docs.
- UKG Nano Crystal intake and evidence classification.
- Cross-harness adapter notes that Merlin, Forge, Sentinel, and Alex can consume.
- Feedback that separates confirmed runtime truth from planned or aspirational
  architecture.

## Evidence Gates

Classify every major claim before integration:

- `confirmed`: verified by current files, commands, tests, logs, or manifests.
- `planned`: implementable but not yet built or verified.
- `aspirational`: useful direction, but unsupported by repo evidence.
- `rejected`: conflicts with verified Camelot runtime state.

Never accept claims of compression, code generation, Z3 proof, zero memory
leaks, or instant rehydration without a reproducible command and artifact.

## Integration Workflow

1. Activate or probe Camelot with the real command surface.
2. Record activation caveats before analysis.
3. Store proposed crystal manifests in `03_VAULT/runtime_state/`.
4. Store engineering critique in `docs/architecture/`.
5. Run the cheapest relevant verification commands before claiming success.

## Learned Rules

Rule 1: [Evidence] - ALWAYS separate confirmed, planned, aspirational, and rejected claims because Camelot lore must not replace runtime truth.
Rule 2: [Security] - NEVER store secrets in harness, crystal, or runtime-state files because Camelot config only records boolean presence flags.
Rule 3: [Runtime] - ALWAYS report boot caveats, failed phases, and locked ports before saying Camelot is fully functional.
